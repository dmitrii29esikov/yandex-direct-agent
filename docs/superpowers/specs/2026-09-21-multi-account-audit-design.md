# Мультиаккаунтный доступ и онлайн-аудит кампаний

**Дата:** 2026-09-21
**Проект:** Yandex Direct Agent (MCP-сервер, `C:\yandex_direct_agent`)
**Статус:** согласовано, реализовано полностью (все 6 этапов)

---

## 1. Задача

Подключаться к произвольному клиентскому аккаунту по трём контурам —
Яндекс.Директ, Яндекс.Метрика, Яндекс.Тег Менеджер — через API, выбирать
аккаунт на уровне вызова, проводить аудит кампаний и выдавать выводы: что
исправить и в каком порядке, чтобы улучшить конверсии.

Ключевое требование заказчика: **минимизировать беспокойство владельцев
аккаунтов**. Клиент делает одно действие — один раз выдаёт доступ.

## 2. Факты из справки Яндекса (проверено)

| Контур | Модель доступа | Запись через API |
|---|---|---|
| Директ | `Client-Login` доступен **только агентствам** ([Агентствам](https://yandex.ru/dev/direct/doc/ru/best-practice/agency)); вне агентства — один токен на аккаунт | полная |
| Метрика | GET-параметр `ulogin` — работа с аккаунтами представительского доступа ([ulogin](https://yandex.ru/dev/metrika/ru/advanced/ulogin)) | цели, счётчики, представители |
| Tag Manager | Доступ определяется токеном (`ytm:read`), переключения логина нет | **только чтение** |

Дополнительно:
- `Use-Operator-Units: true` — расходуем свои баллы, а не баллы клиента.
- Яндекс рекомендует отдельный логин-представитель под приложение: смена
  пароля клиентом тогда не убивает токен.
- `GET /management/v1/clients?counters=...` возвращает клиентов Директа с
  полем `chief_login` — это готовый логин для `Client-Login`, то есть
  автоматическая связка «счётчик ⇄ аккаунт Директа».
- Кросс-тест подтвердил: три токена проекта строго разграничены по скоупам,
  один вместо другого не работает.

## 3. Архитектура

### 3.1 Разделение ответственности

- `data/accounts.json` — реестр: доступы и привязки, **без токенов** (можно в git).
- `secrets/secrets.json` — токены (в `.gitignore`, без шифрования: для 3–5
  клиентов достаточно; переезд на шифрование не потребует менять остальной код).
- `access.py` — **единственное место**, где живёт разница режимов.
- `accounts_store.py` — реестр, секрет-стор, разрешение ID → аккаунт.
- `audit_engine/` — движок аудита.
- `tools/*` — MCP-инструменты, получают `account` и не знают про токены.

### 3.2 Гибридные режимы

```json
"direct": { "mode": "agency", "client_login": "anton-anima" }
```
- `agency` — один агентский токен + `Client-Login` + `Use-Operator-Units`.
- `token` — свой токен аккаунта.

Оба режима обслуживает один код; перевод клиента на агентский режим — правка
одного поля в реестре.

### 3.3 Разрешение аккаунта

`accounts_store.resolve()` принимает имя аккаунта **или любой знакомый ID**:
ID счётчика Метрики, ID контейнера YTM, `client_login`, `client_id`. Это
снимает необходимость объяснять агенту, к какому аккаунту относится ID.

### 3.4 Онбординг

`tools/accounts.py`: `discover_accounts`, `list_accounts`, `check_account`,
`describe_account`, `add_account`, `set_account_tokens`, `link_account_data`,
`oauth_link`.

Токены наружу не отдаются никогда — только маска вида `y0__…f3a2`.

### 3.5 Данные YTM

API Tag Manager не поддерживает запись, поэтому «правки» по YTM выдаются как
чек-лист для интерфейса с пометкой `ytm_ui`.

## 4. Движок аудита

### 4.1 Находка (Finding)

Каждая находка несёт **доказательства** и **действие**:
`code`, `contour`, `severity`, `title`, `detail`, `object_*`, `evidence`,
`fix`, `fixable` (auto/manual/ytm_ui), `money`, `blocking`, `impact`.

### 4.2 Реестр проверок (29 проверок)

- **direct (14):** структура, тексты, ставки/бюджет, модерация.
- **metrica (6):** цели, качество данных.
- **ytm (5):** теги, триггеры, переменные, дубликаты.
- **cross (4):** связки между контурами — самая ценная группа.

Массовые проблемы агрегируются по кампании, чтобы отчёт оставался списком
задач, а не свалкой из тысяч строк.

### 4.3 Приоритизация

```
impact = база(severity)
       + деньги под риском (лог расхода)
       + расход без конверсий (+25)
       + блокирует другие фиксы (+15)
       ± стоимость исправления (auto +5 / ytm_ui −5)
```

### 4.4 Диагнозы

Слой `diagnose()` склеивает находки в корневые причины с формулировкой
«почему это важно», «последствия» и упорядоченными действиями. Диагнозы
сортируются по impact: человек читает сверху вниз.

### 4.5 Вывод

- markdown в чат (топ-N диагнозов + сводка по кодам + «Не проверено»);
- XLSX `data/audits/audit_<account>_<ts>.xlsx` (листы «Диагнозы», «Находки»,
  «Не проверено», «Связка»);
- `remediation_<account>_<ts>.md` — чек-лист правок.

### 4.6 Режимы

`report` — только чтение, по умолчанию.

`apply` — применение автоматических правок (`fixable: auto`) с тремя
предохранителями:
1. без `confirm=True` возвращается только план (dry-run) — ни одного запроса
   на изменение;
2. каждая правка до применения описана парой `before` / `after`;
3. после применения пишется журнал `data/audits/apply_*.json`, откат —
   `rollback_apply`.

Реестр правок — `fixers.py`. На сегодня реализовано два фиксера:
`DIRECT.TEXT_LENGTH` (сокращение заголовков до 56 и текстов до 81 символа,
по границе слова) и `DIRECT.NO_DAILY_BUDGET` (значение берётся из реестра;
если не задано — фиксер бездействует). Всё остальное остаётся ручным, и
инструмент честно возвращает блок `not_automatic`.

Наблюдение из реального dry-run: автосокращение может убрать призыв к
действию в конце текста. Поэтому план всегда просматривается человеком
перед подтверждением.

## 5. Надёжность

- **Изоляция аккаунтов:** отозванный токен у одного клиента не ломает прогон
  остальных (`audit_all_accounts`).
- **Человеческие ошибки:** коды Direct (53, 54, 58, 152, 8800) и HTTP-статусы
  Метрики/YTM переводятся в понятный диагноз.
- **Баллы:** читаем заголовок `Units`, предупреждаем при остатке < 20 %.
- **Самовосстановление полей:** при ошибке 8000 («неизвестное поле») движок
  сам убирает лишние поля из запроса и повторяет — защита от изменений в API.
- **«Не проверено»:** любая недоступная проверка честно попадает в отчёт, а не
  молча исчезает.

## 6. Ограничения

1. Директ вне агентства: N аккаунтов = N токенов.
2. Tag Manager: правки через API невозможны.
3. `campaigns.get` не отдаёт `CounterIds`, поэтому проверка
   `CROSS.GOALS_MISSING_IN_DIRECT` пишет в «Примечания», что она пропущена.
4. Проверка звука/видео-креативов не реализована.
5. Откат возможен не для всего: снятие дневного бюджета через API
   невозможно, такие случаи перечисляются в блоке `cannot_rollback`.
